# 09 · 任务流水线与回测台账

> **层级**：L2a 工作规范 ｜ **前置阅读**：[02-工程规范](02-工程规范.md)、[03-测试策略](03-测试策略.md) ｜ **何时读我**：登记/推进/验收任何任务时；查询回测结果时；分析打回原因时

## 一、定位

两件事，一个目的：

1. **任务全生命周期留痕**：开发 → 测试 → 数据验证 → 功能验收 → 结论，逐阶段入库
2. **回测结果持久化**：03-L4.5 回测台账的具体实现

目的：杜绝"agent 口头说做完了/测好了"——状态在数据库里，不在对话里。

## 二、设计原则

- **数据库是唯一事实来源**：任务状态、回测结论以 DB 记录为准
- **事件流只增不改**：`task_events` 记录全部流转历史（档案型）；`tasks` 存当前状态（状态型，覆盖更新）
- **agent 只能通过 CLI 迁移状态**：CLI 内置状态机校验，跳阶段、无证据的"通过"一律拒绝——守规矩靠机制，不靠 prompt
- **零运维**：DuckDB（与 ADR-0003 同栈），库文件存 `${ZX_DATA_ROOT}/taskdb/`（ADR-0007）

## 三、任务生命周期

```
登记(新行) → 开发 → 测试 → 数据验证 → 功能验收 → 结论
                ↑________ 打回（记录次数+原因，回到对应阶段）________↓
```

- 每个阶段标记"通过"**必须附证据**：CI 绿记录 / 测试报告路径 / 数据验证记录 / 验收对照表
- 阶段可标"不适用"（如纯文档任务免数据验证），必须写理由
- 与 02-DoD 的关系：DoD 是"通过"的判定细则，流水线是载体——阶段通过 = 该阶段对应 DoD 项全绿

## 四、打回与踩坑登记（防死循环）

- 打回必填**结构化原因**：测试不充分 / 数据异常 / 契约不符 / 实现缺陷 / 其他（+ 说明），计数 +1
- **同一任务打回 ≥ 3 次 → 自动挂起**，升级用户：先分析根因，再决定继续 / 拆分 / 放弃（阈值可调）
- 同一原因重复出现（跨任务）→ 登记**坑表**（现象 / 根因 / 规避方法 / 关联任务）
- **agent 开工前必须检索坑表**（已写入 README 交接协议第 4 步）

## 五、回测台账持久化（03-4.5 的实现）

- 每次回测一行记录：策略+版本、参数哈希、数据区间、成本假设、样本内/外指标、第 N 次回测、报告路径、状态（通过/失败/作废）
- 净值曲线等大件存 `${ZX_DATA_ROOT}/backtests/`，DB 存路径
- **任何"测好了"的汇报必须附 backtest_id**；策略报告引用编号并披露"第 N 次回测"（03-4.5）

## 六、数据模型（草案，实现时可调）

| 表 | 关键字段 |
|---|---|
| `tasks` | id、标题、类型(feat/fix/docs/data)、关联 Step/文档、当前阶段、状态、打回计数、创建/更新时间 |
| `task_events` | id、task_id、时间、操作者(agent/用户)、动作、源阶段→目标阶段、原因、证据路径 |
| `backtests` | id、task_id、策略、版本/参数哈希、数据区间、成本假设、样本内外指标、第 N 次、报告路径、状态 |
| `pitfalls` | id、现象、根因、规避方法、关联任务、登记时间 |
| `signals` | id、股票、方向(T出/T入)、参考价、触发策略/组合、双源校验结果、推送时间、T+1/T+3/T+5 三档复盘得分 |
| `positions` | 股票、底仓数量、可做T 仓位、更新时间（用户维护，07 第二节） |

## 七、展示

- **初期 CLI**：任务看板（进行中任务 + 当前阶段 + 打回次数一屏看全）、单任务时间线（事件流）、坑表浏览、回测台账查询
- **中期（候选）**：并入目标 1 站点的看板页，随站点演进评估

## 八、agent 交互规则

1. 开工：登记任务（关联 Step 与验收文档）→ 按 README 起手式复述边界
2. 阶段完成：CLI 迁移状态 + 附证据
3. 打回：结构化原因 + 计数；≥3 次触发挂起
4. 结论：由 agent 给出并入库；功能验收的最终确认权在用户
5. **过渡例外**（用户决议 2026-09-18）：`tasks` 表本身是 Step 0d 的产出，无法给自己留痕——0a~0c 免登记；0d 的验收以本文第九节 + CLI 自测为准；**自 Step 1 起，任何任务不登记即开工视为违规**

## 九、验收标准（Step 0d）

1. 任务可走通 登记→开发→测试→数据验证→功能验收→结论 全流程
2. 非法状态迁移（跳阶段、无证据通过）被 CLI 拒绝（状态机测试）
3. 打回 ≥3 次自动挂起；坑表可登记、可检索
4. 回测台账可写入/查询，报告能引用 backtest_id

## 十、会话交接棒（夜间无人值守的最小上下文契约）

> 形态与动机见 [ADR-0023](adr/0023-夜间无人值守接力驱动.md)。**本节是交接棒格式的单一事实来源**；
> `tools/night/handoff.tmpl.md` 只是可填写骨架，不复述规则。

1. **定位**：一任务一全新会话（驱动 `tools/night_driver.py`），任务间的上下文只靠一份交接棒
   传递。状态的唯一事实来源仍是 taskdb（§一）——交接棒只承载「这一刀」的最小进度，不承载状态。
2. **格式**：`reports/night/<date>/handoff-NNN-<taskid>.md`，六节强制，缺节即违规：

   ```
   # 交接棒 · <task-id> · <完成|挂起|部分完成>
   ## 一、结论与产出物（≤10 行）
   ## 二、关键决策（逐条：选了什么 / 为什么 / 代价是什么）
   ## 三、触碰的文件（仅路径）
   ## 四、证据指针（pytest 尾行、coverage 数字、backtest_id、commit sha、CI run id）
   ## 五、开着的口子 / 待用户裁决（标注对应 Q1 哪个节点）
   ## 六、建议的下一任务（一句话 + 路线图 Step 依据）
   ```

3. **容量与禁令**：≤150 行、≤8KB；**只给指针不给内容**——禁止贴文件内容、对话史、完整日志
   （需要留证就写路径与命令，让人能重放）。驱动校验节头与容量，不校验内容真伪。
4. **无人值守权限边界**：`zx-task advance` 最多推进到**数据验证**；`conclude`/`resume`/`abandon`
   是用户裁决位（§三、§八-4），夜间永不调用。Q1 四节点（05 §四）事项只写进「待用户裁决」。
5. **晨间产物**（ADR-0007：不进文档库）：`reports/night-shift-<date>.md`（今晚上线了什么 /
   证据可重放 / 还开着的口子）+ `reports/decision-pack-<date>.md`（逐条选项 + 推荐 + 可重放命令）。
