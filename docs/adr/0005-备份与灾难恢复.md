# ADR-0005 · 备份与灾难恢复

> **层级**：L3 决策档案 ｜ **前置阅读**：[ADR-0003](0003-存储方案.md) ｜ **何时读我**：质疑备份方案时（变更须新建 ADR）

- 状态：Accepted（2026-09-17）

## 背景

上一版项目以"删除仓库 + 重置服务器"告终，代码与数据全毁。本次数据集中于 E 盘（ADR-0003），单盘即单点。必须假设：磁盘会坏、误删会发生、系统会重装。

## 决定

1. **备份对象**：E 盘数据（Parquet/DuckDB/回测产物）+ git 仓库（含文档）+ 任务流水线库
2. **介质**：**网盘**（用户选定，零成本；接受其速度与稳定性一般的代价）
3. **频率**：每日 02:00 增量 + 每周日 03:00 全量；保留最近 3 代全量
4. **实施时机**：**延后至阶段二完成、有真实数据之后启用**（用户决议：现在没有内容可备份）；首个备份任务随 Step 5 验收落地
5. **恢复演练**：启用时完成首次演练，此后每季度至少一次——随机挑一个数据集从备份恢复到临时目录并校验可读。**没演练过的备份等于没有备份**
6. git 仓库推送到远端（GitHub/Gitee 私有库），代码与文档天然双份

## 后果

- 正面：任何单点故障最多损失一天数据增量；零成本
- 代价：网盘同步速度与稳定性一般，大数据量全量同步耗时需观察；恢复依赖网盘可用性

## 补充决定（2026-09-20，Step 5f 落地时补）

上面六条给的是**策略**：备份什么、多久一次、留几代、要演练。要落成一条命令，还差四个机械口径
——"增量"到底拷什么、拿什么判"这个文件变了"、恢复怎么知道自己恢复对了、备份根配在哪里。这一节
只写那四个答案，**策略一条没动**，动的全是"怎么执行"。

### 补充决定一：备份根是第二个配置项，没配就拒运行，且不许套在数据根里

`ZX_BACKUP_ROOT`（`config.backup_dir()`）。两条判定：

- 未设置 → 退出码 2，话要说成"没配备份根"，不能说成"没有要备份的文件"——后者听起来像备份成功
  了。理由与 ADR-0013 决定 3 那条同源：一个悄悄不鉴权的站点、一份悄悄不落盘的备份，都是"一切
  正常"形状的失败，而那正是最贵的一种。
- 备份根与数据根互相包含 → 拒绝。自我包含的一棵树，每一代都会把上一代套进自己的扫描里，"保留
  3 代全量"随即变成递归；而最省事的写法（`<数据根>/backup/`）恰好就是这个写法。

**不给默认值**：备份根没有"合理机器上它就在那儿"的位置——网盘挂在哪由人定。给一个默认值等于在
ADR-0007 那条"路径只能从配置读"上再开一个洞，还要顺带扩 `tests/test_path_hygiene.py` 的豁免点。

### 补充决定二：全量是完整文件树，增量是自基线以来的变化，代与代之间不共享字节

硬链接（`rsync --link-dest` 那套）能把每代成本压到"变化量"，但决定 2 把介质定成了网盘：多数同步
客户端不把硬链接语义传过去，跨设备与同步中断时还可能把一条链接拆成两份副本。一份会漂的优化不算
优化。于是布局是：

```
<备份根>/state.json                       # 基线指针 + 上次扫描的 (size, mtime_ns) 表
<备份根>/full/<YYYY-MM-DD>/…              # 完整树，逐代独立可恢复
<备份根>/delta/<YYYY-MM-DD>/…              # 只含自基线以来新增/改动的文件
<备份根>/delta/<YYYY-MM-DD>/manifest.json  # 这些文件的 sha256 + 这一代删掉了哪些路径
```

恢复任意一天 = 最近一个不晚于它的 full，再按日期顺序叠加其后的 delta（新增与改动的覆盖，`deleted`
里的那些抹掉）。裁剪只在**新一代全量写成功之后**发生（先写下新的、最后删旧的）：`full/` 留最新三
个目录，早于最老那一代的 delta 一并删——它们的基线已经不在了，留着也拼不出任何东西。

代价：网盘上同时放 3 份全量。数据根今天实测 **366 个文件 / 9.08 MiB**（2026-09-20 第一次 `full`
的数，`du -sh` 出 9.2 MB——原先这里写的"2.4 MB"是更早一次记下的数，已经不对了，见坑 #34），日线
满 5 年是数十 GB 级 → 决定 4 那句"耗时需观察"要按 **3×全量 + 每日增量** 这个体量去观察，网盘配额
是同一件事。今天这个体量下全量拷贝实测 0.18 秒、一次演练 0.35 秒。

### 补充决定三：判"变没变"用 (size, mtime_ns)，哈希只在要拷的那一刻算

数据根里的东西绝大多数写一次就不再变：一个 Parquet 分区文件代表一个 `(dataset, year, symbol)`，
同日重跑盘上不动（Step 3 验收 3 那条幂等语义就是它的保证）；`reports/`、`backtests/`、`golden/`
落定即不动。真会变的只有 `taskdb/` 那个 DuckDB 与 `site/recent.json` 这一类小文件。全树 sha256
是要在几百 GB 上每晚走一遍的，而它买到的信息在这类文件上 `(size, mtime_ns)` 已经给了。

所以：扫描按 `(size, mtime_ns)` 决定拷不拷，**被判要拷的文件在拷完之后算一次 sha256 写进
manifest**，校验放在恢复侧（补充决定四）。读的时候真检一遍，比扫的时候全检一遍更值。

代价：有人手工把一个文件改成同样的大小与同样的 mtime，这一代就看不见那次改动。这条没有兜底，是
本 ADR 明确接受的盲点——它要成立得同时满足"原地改"与"改完不碰 mtime"，而数据根里唯一允许原地变
的那个文件是 DuckDB，它的写法不是这个样子。

盯盘的人要知道的一个口径：真数据根上**没有"安静的一天"**。`full`/`incr` 每次都把当次的报告归档进
`reports/backup/`（决定"跑过就得留下能查的东西"），而 `reports/` 在被扫的树里——所以 `incr` 最少
也会报"新增 1"，那一个就是它自己昨天那份报告。这不是漏了什么，别把它读成"盘上每天有东西在变"。

### 补充决定四："恢复成功"的判据是可读，不是存在

`zx-backup verify` 做三件事：挑一个数据集恢复到临时目录 → 把备份里的字节与 manifest 记的 sha256
逐文件对一遍 → 用 `storage.query.depth` 真读一遍那个数据集（分区目录的找法与站点取数同一条路）。
报告落 `reports/backup/<日期>-verify.md`——文件名带动作，因为同一天可能有 `full`、`incr`、`verify`
三份报告，只写日期的话后一份会把前一份盖掉，而"那天演练过吗"恰恰是要查的那件事。

为什么字节对了还不算完：Parquet 写到一半被同步客户端截断是真实发生过的坏法，而它在"文件在不在"
和"多大"上都像个好文件。sha256 是在备份侧拷完之后算的，它保证的是"备份里那份没坏"；重新读一次
保证的是另一种——"网盘同步又把它写坏了"。

决定 5 那句"没演练过的备份等于没有备份"到这儿才有一条命令可跑：季度演练 = 跑一次 `verify`，而
不是每季度想起来一次。

### 补充决定五：定时交给系统，工具不常驻、不自排

`zx-backup incr | full | verify` 各跑一遍就退出。02 §六 里那些"每天要落盘的东西"都是被调度者，
调度器不归这个项目管：cron / systemd timer 装到用户机器上是改机器的服务，属要先点头的动作；
unit 文件随仓库给出，装与不装由人（05 Q1 同一条）。

两份的样子（WSL2 与 Linux 同形；Windows 侧用任务计划程序，命令换成同一组）：

```cron
# crontab -e：每日 02:00 增量，每周日 03:00 全量 + 演练（决定 3 的那三班）
0 2 * * 1-6   cd ~/git_code/zhixing_quant && ZX_BACKUP_ROOT=/mnt/e/zhixing_backup uv run zx-backup incr
0 3 * * 0     cd ~/git_code/zhixing_quant && ZX_BACKUP_ROOT=/mnt/e/zhixing_backup uv run zx-backup full
15 3 * * 0    cd ~/git_code/zhixing_quant && ZX_BACKUP_ROOT=/mnt/e/zhixing_backup uv run zx-backup verify --into /tmp/zx_drill
```

```ini
# systemd 侧：一个 service + 三个 timer（`ZX_BACKUP_ROOT` 从 environment 或 user unit 里给）
[Service]
Type=oneshot
WorkingDirectory=%h/git_code/zhixing_quant
Environment=ZX_BACKUP_ROOT=/mnt/e/zhixing_backup
ExecStart=%h/.local/bin/uv run zx-backup incr
```

排班里有三条不是显而易见、却会咬人的：

- **演练排在全量之后 15 分钟**（代价二）：`verify` 读的是刚写完的那一代，排在 02:00 那一班就等于
  天天验昨天。
- **`--into` 给一个 `/tmp` 下的路径，且不删**：工具不删恢复目标（删错目录比留一个临时目录贵得多），
  所以那行后面跟一句自己的清理，或者交给 `/tmp` 的重启。
- **退出码非 0 得有人听见**：cron 只在有输出时发信，而这三条命令每次都往 stdout 打一页报告——
  也就是说每次都发。真正会漏的是"根本没跑"：机器那天没开着，那一班就没了，没有补跑。05 那条
  "盘后任务错过就不补"在这里同样成立，但备份错过一天是**没有告警**的，所以 Runbook 里那句
  "看 `reports/backup/` 的日期连不连续"是人来做的，不是机器。

## 补充后果

- 正面：备份与恢复各自成了一条命令，"备份成功"第一次有了可判的判据——恢复出来读得到，而不是传上去了。
- 代价一：备份根必须配在**只出不进**的同步目录里。双向同步加上另一台机器上那份旧数据根，会把刚
  备份完的目录倒灌清空；这是网盘的真实坏法，而工具判不了它（工具看得见的是本地那个目录）。这条
  只能写进 Runbook，与 ADR-0006 那台机器一起交代。
- 代价二：`verify` 要真读盘，比 `incr` 慢一个量级。所以它排在每周日全量之后，不排在每日 02:00 那一班。
- 代价三：恢复时"挑哪个数据集来验"由 `storage/layout.py` 那四个目录名决定，不由备份自己记的一份
  账决定。备份不另立第二份真源，理由与 ADR-0011 决定 5、ADR-0012 决定 2 同一条。
