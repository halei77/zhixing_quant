# ADR-0001 · 技术栈选型

> **层级**：L3 决策档案 ｜ **前置阅读**：[02-工程规范](../02-工程规范.md) ｜ **何时读我**：质疑技术栈选择时（变更须新建 ADR）

- 状态：Accepted（2026-09-17）
- 决策人：用户 + 主线 agent

## 背景

项目重启，需确定主力技术栈。约束条件：

1. 单人维护，长期可维护性优先（上一版死于维护心累）
2. 用户不阅读代码 → 用户的界面是文档与报告，语言生态差异对用户感知弱
3. 需要丰富的量化生态：数据源 SDK（akshare）、DataFrame 校验（pandera）、属性测试（hypothesis）、指标对照（TA-Lib）

## 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. Python** | 量化生态最全；akshare 原生；测试工具链成熟 | 高并发/Tick 级性能一般 |
| B. C#/.NET | 用户机器上有 .NET 开发痕迹；性能好 | 量化数据源生态薄弱，akshare 类库需自行封装，单人维护成本高 |
| C. 混合（Python 数据 + C# 服务） | 各取所长 | 双栈 = 双倍维护，违背约束 1 |

## 决定

**方案 A：Python 全家桶。** 工具链明细见 02-工程规范第一节。

## 后果

- 正面：数据源适配、测试、校验全部有现成生态，开发速度最快
- 负面与缓解：Tick 级/高频场景性能不足 → 届时用 polars/DuckDB 向量化兜底；真到瓶颈再引入 Rust 扩展（写入路线图"不做"清单的解锁条件）
- 附带决定：用户不看代码 → 所有产出物（报告、测试结果、数据质量日报）必须按"给人读"的标准设计
