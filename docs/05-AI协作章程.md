## 一、上一版模式与失败根因

上一版：3 个 Gemini CLI agent（开发 / 管理 / 测试），宽松授权、独立并行。

| 现象 | 根因 |
|---|---|
| 测试不严谨 | 测试 agent 的目标是"证明能跑"而非"找出错误"——LLM 默认讨好型验证 |
| 低级错误多 | 无机器可执行的验收标准，"管理 agent"用自然语言验收 = 没有验收 |
| 效率低 | 三 agent 并行，接口契约靠 prompt 口头约定，集成时错误集中爆发 |

**核心教训：质量来自不可绕过的机器门禁，不来自更多的 agent。**

## 二、本次模式：单主线 + 机器验收 + 一次性对抗评审

```
        ┌──────────────────────────────────────────┐
        │                用户（决策层）              │
        │  定契约、批文档、裁决开放问题、批黄金样本    │
        └───────────────┬──────────────────────────┘
                        │ 指令 / 确认
                        ▼
        ┌──────────────────────────────────────────┐
        │            主线 agent（常驻 × 1）          │
        │  架构 + 开发 + 文档 + 测试编写，单线程推进   │
        └───────────────┬──────────────────────────┘
                        │ 产出（代码+测试+文档）
                        ▼
        ┌──────────────────────────────────────────┐
        │          CI 机器门禁（唯一裁判）            │
        │  ruff → mypy --strict → pytest → 契约测试 │
        └───────────────┬──────────────────────────┘
                        │ 关键节点触发
                        ▼
        ┌──────────────────────────────────────────┐
        │      对抗评审子代理（一次性，挑完即销毁）     │
        │  唯一任务：挑刺。不挑出新问题不罢休          │
        └──────────────────────────────────────────┘
```

### 规则

1. **单主线**：任何时刻只有一个主线 agent 在推进，杜绝并行写代码再合并。
2. **机器验收唯一**：完成的定义 = CI 全绿（02-工程规范 DoD），agent 自述不算。
3. **对抗评审触发点**：新数据源适配器完成时；回测引擎完成时；任何策略合入 main 前；用户随时可手动触发。
4. **测试编写用对抗性 prompt**：要求"假设这段代码有 bug，写出让它暴露的测试"，而非"为这段代码写测试"。
5. **文档变更权限**：agent 可起草文档，但**文档的采纳必须用户确认**——文档是契约层，agent 不能自己改契约再按新契约写代码。
6. **任务流水线**：所有开发任务在任务系统登记并逐阶段留痕（[09](09-任务流水线与回测台账.md)）；打回必填原因，同一任务打回 ≥3 次自动挂起并升级用户。

## 三、对抗性测试 prompt 模板

```
你是对抗性测试工程师。阅读以下实现代码，你的任务是假设它一定存在 bug，
写出能让 bug 暴露的测试：
1. 先列出你怀疑的缺陷点（至少 3 个：边界、并发/顺序、数值精度、异常输入）
2. 为每个怀疑点写出 pytest 用例
3. 禁止写"验证正常路径"的测试——正常路径由主线负责，你只负责找茬
4. 如果一个 bug 都找不到，明确说明"未能发现缺陷"，不允许为了交差写无意义断言
```

## 四、已决事项（2026-09-17 用户批准）

| # | 事项 | 决议 |
|---|---|---|
| Q1 | **用户确认节点** | 4 处必须用户确认：① 文档采纳；② 每个 Step 验收（含版本上线）；③ 黄金样本更新；④ 策略合入 main。其余 agent 自主推进。**日常数据发布**（验证通过后 WSL2→阿里云）自动执行，不占确认节点 |
| Q2 | **对抗评审深度** | 关键节点全量评审（挑刺到找不出新问题为止）；日常提交只过 CI，不逐次评审 |
| Q3 | **测试权限** | L0/L1/L3 可自主补齐；L2 黄金样本可提议、更新必须用户批准；L4 测试框架改动必须用户审。**测试只增不减**：删除测试、放宽断言、调大容差、加 skip——一律需用户批准 |
| Q4 | **测试粒度** | 按 03 第三节"测试粒度原则"表执行；核心模块清单（`quality`/`backtest`/`strategy`/`tasks`）维护在 02-DoD，变更需用户批准 |
| Q5 | **agent 记忆边界** | 跨 session 的决策与教训一律写入文档/ADR/坑表，不依赖 agent 私有记忆——换 agent 不丢上下文 |
| Q6 | **第二常驻 agent** | 暂不引入，保持单主线 + 一次性评审代理；将来需要 7×24 数据监控时再设专职"运维 agent" |
